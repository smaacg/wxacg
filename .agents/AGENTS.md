# Antigravity 專案開發規範

## 1. 全域語言規範

* 所有一般回覆、分析、計畫、任務清單、建議與說明，皆使用台灣繁體中文。
* 程式碼註解也優先使用繁體中文。
* 技術名詞、API 名稱、函式名稱、變數名稱、套件名稱、指令與程式碼本身可保留原文。
* 不得無故切換成英文或簡體中文。
* 回覆應簡潔、直接、清楚，避免不必要的贅述。

---

# 2. 修改程式碼前必須確認

AI 在實際修改、新增或刪除任何檔案前，必須：

1. 先理解目前專案架構。
2. 查看與任務相關的原始碼。
3. 如果是 Bug，先查看相關 Log、錯誤訊息與設定。
4. 說明目前判斷的問題原因。
5. 提出修改方案。
6. 列出預計修改的檔案。
7. 說明可能影響的現有功能。
8. 等使用者明確同意後，才能開始修改。

使用者未明確同意前：

* 不得修改程式碼。
* 不得新增檔案。
* 不得刪除檔案。
* 不得重構程式架構。

---

# 3. 最小範圍修改

* 只修改與目前任務直接相關的程式碼。
* 不得順便修改無關程式。
* 不得為了程式碼「看起來更漂亮」而任意重新排版。
* 不得任意重新命名既有變數、函式、類別或檔案。
* 不得擅自改變既有資料流程。
* 不得擅自改變既有設定。

---

# 4. 禁止擅自重構

在一般維護、Bug 修正或增加功能時：

* 不得擅自拆分模組。
* 不得擅自合併模組。
* 不得擅自更換框架。
* 不得擅自更換核心技術方案。
* 不得因為認為另一種架構比較漂亮，就改寫現有架構。

如果認為重構確實有必要：

1. 先說明原因。
2. 說明影響。
3. 提出重構方案。
4. 等使用者明確同意後才能執行。

---

# 5. 註解保留規範

* 嚴禁無故刪除原有中文註解。
* 替換或重構程式碼時，必須保留原有 Docblocks 與行內註解。
* 不得為了縮短程式碼而刪除註解。
* 如果發現原有註解與實際程式邏輯不一致，先告知使用者。
* 修改註解時，必須確保修改後內容仍然正確。

---

# 6. Debug 與錯誤處理規範

## 6.1 不瞎猜

遇到以下問題：

* Error
* Exception
* Warning
* Fatal Error
* API 錯誤
* 程式行為異常

必須優先查看：

1. 錯誤訊息
2. Log
3. 相關原始碼
4. 相關設定
5. 錯誤發生前後的資料流程
6. API Request / Response
7. 必要的外部服務文件

不得只根據錯誤訊息表面文字直接修改程式。

如果證據不足：

* 必須明確說明目前只是推測。
* 不得把推測描述成確定原因。
* 應繼續調查取得更多證據。

---

# 7. 禁止吞掉錯誤

嚴禁為了讓測試通過而：

* 使用空白 `except: pass`
* 使用無意義的 `try-except`
* 靜默忽略 Exception
* 靜默忽略 Warning
* 隱藏 API 錯誤
* 將錯誤轉換成假成功

任何異常都必須：

* 保留適當錯誤資訊。
* 寫入適當 Log。
* 找出問題原因。
* 在合理情況下提供可追蹤的錯誤訊息。

---

# 8. API 與資料介面規範

凡修改以下內容：

* AJAX Payload
* REST API
* API Request
* API Response
* JSON 結構
* Request Parameters
* Response Parameters
* 資料表欄位
* 前端資料模型
* 後端資料模型

必須同時檢查：

【傳送端】
↓
【資料格式】
↓
【API / 通訊介面】
↓
【接收端】
↓
【資料處理】
↓
【資料儲存】

不得只修改其中一端。

修改完成後必須確認前後端資料格式一致。

---

# 9. 第三方依賴規範

除非確實必要：

* 不得任意新增第三方套件。
* 不得任意下載陌生套件。
* 優先使用目前專案既有依賴。
* 優先使用語言與框架原生功能。

如果認為新增套件確實必要：

1. 說明為什麼現有工具無法完成。
2. 說明套件名稱。
3. 說明套件用途。
4. 說明可能增加的維護與安全風險。
5. 等使用者確認後再安裝。

---

# 10. Git 規範

## 10.1 嚴禁自動 Push

AI 修改程式後：

* 絕對不得自行執行 `git push`。
* 絕對不得自行部署 Production。
* 絕對不得自行發布正式版本。

只有在使用者明確表示以下類似意思時才能執行：

* 「確認 OK」
* 「可以 Push」
* 「可以部署」
* 「請幫我 Push」
* 「確認可以上線」

---

## 10.2 Commit 前檢查

執行 `git commit` 前必須：

1. 確認所有編輯中的檔案已存檔。
2. 執行 `git status`。
3. 查看 `git diff`。
4. 確認沒有無關修改。
5. 確認沒有敏感資訊。
6. 確認相關測試結果。

如果發現不明或無關修改，不得自行加入 Commit。

---

## 10.3 Commit 訊息

必須使用 Conventional Commits：

* `feat:`
* `fix:`
* `refactor:`
* `chore:`
* `docs:`
* `test:`
* `perf:`

Commit 訊息必須使用繁體中文清楚描述實際修改內容。

例如：

`feat: 新增 WordPress 標籤快取機制`

`fix: 修正 API 錯誤處理`

---

# 11. 部署規範

嚴禁自動部署。

標準流程：

【AI 修改】
↓
【本地測試】
↓
【使用者確認】
↓
【使用者明確授權】
↓
【Commit】
↓
【Push / 部署】

未取得使用者明確授權前：

* 不得 `git push`
* 不得 `gcloud run deploy`
* 不得部署 Cloud Run
* 不得部署 WordPress
* 不得發布 Production
* 不得執行任何會直接影響正式環境的操作

---

# 12. 破壞性指令

以下操作執行前必須取得使用者明確確認：

* `git reset --hard`
* `git clean`
* `rm -rf`
* 大量刪除檔案
* 覆蓋重要檔案
* DROP TABLE
* 大量刪除資料
* Production 資料修改
* 任何可能造成不可逆資料遺失的操作

執行前必須明確告知：

1. 指令會做什麼。
2. 哪些資料可能受到影響。
3. 是否可以復原。

---

# 13. 測試規範

程式修改完成後：

1. 執行與修改內容相關的測試。
2. 檢查語法錯誤。
3. 檢查 Import / Dependency。
4. 檢查 API Request / Response。
5. 檢查相關 Log。
6. 如果測試失敗，不得忽略。
7. 必須向使用者回報測試結果。

如果無法測試：

* 必須明確告知無法測試的原因。
* 不得宣稱「測試通過」。

---

# 14. 工作流程

一般任務遵循：

【理解需求】
↓
【分析現有程式】
↓
【查看 Log / 證據】
↓
【提出方案】
↓
【等待使用者確認】
↓
【修改程式】
↓
【本地測試】
↓
【回報結果】
↓
【等待使用者確認】
↓
【Commit / Push / 部署】

除非使用者明確要求直接執行，否則不得跳過確認流程。

---

# 15. 最重要的原則

優先順序：

1. 正確性
2. 安全性
3. 可維護性
4. 最小修改範圍
5. 保持既有架構
6. 清楚的錯誤處理
7. 可追蹤的 Git 歷史

不得為了：

* 速度
* 程式碼看起來更漂亮
* 測試暫時通過
* 減少輸出內容

而犧牲以上原則。
