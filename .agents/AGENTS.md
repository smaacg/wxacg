# 部署與 Commit 規範
⚠️ **這是一個強制性的系統規則，必須在任何時候被嚴格遵守：**

- **嚴禁自動部署**：當 AI 修改或新增了任何程式碼後，**絕對不可以**在沒有取得使用者明確同意的情況下，自行執行 `git push` 或是任何部署指令。
- **佈署前強制存檔與檢查**：執行 `git commit` 或部署動作前，務必確認所有編輯中的檔案皆已存檔，避免推送舊程式碼。
- **強制確認流程**：
  1. AI 修改完程式碼後，必須請使用者先在本地端 (Local) 進行測試與確認。
  2. 只有在使用者明確回覆「確認 OK」、「可以佈署」或類似的肯定語句後，AI 才能執行 `git push` 或後續的部署流程。
- **破壞性指令確認**：執行任何會刪除資料或覆蓋檔案的破壞性指令（如 `git reset --hard`, `rm -rf`, `git clean` 等）前，必須再三向使用者確認。
- **Commit 訊息規範**：必須使用 Conventional Commits 標準前綴（如 `feat:`, `fix:`, `chore:`, `refactor:`），並且內容必須用繁體中文清楚描述具體修改了什麼。

# 程式碼修改與除錯規範
- **嚴禁偷刪註解**：在替換或重構程式碼時，必須「原封不動」地保留原本寫的中文註解（Docblocks 或行內註解），絕對不能為了縮短輸出版面而隨意省略。
- **最小範圍修改**：只修改跟當前任務有關的程式碼，嚴禁隨意更動無關的排版或變數命名，以保持乾淨的 Git 歷史紀錄。
- **不瞎猜原則**：當看到錯誤訊息（例如 Error Code、Fatal Error 等）時，AI 必須主動去查看對應的 Log 檔或原始碼，找出 100% 的證據後才能動手修改，嚴禁盲目瞎猜。
- **修改前須經確認**：AI 在本地修改或更新任何程式碼前，必須要跟開發人員充分討論並給予方案指引；只有在雙方就執行對策達成意念不二之認證、並獲得了授權人的一句同意許可背書之後，才能著手開始進行對系統實際檔案代碼的寫入及改打作業。

# 語言與輸出規範
⚠️ **全域語言限制：必須全面使用繁體中文。**
- **涵蓋範圍**：包含一般回覆、思考過程（Thought）、任務清單（Plans/Tasks）、分析、建議與程式碼註解。
- **嚴格禁令**：嚴禁預設或隨意切換回英文，與團隊溝通及產出皆須以繁體中文為主。
- **回答風格與精簡原則**：回答與解釋的詞彙務必簡潔明瞭，直接切入重點，避免贅字、廢話或無意義的浮誇描述。可以偶爾加上適度的鼓勵或激勵話語，但不可頻繁出現，維持直白乾淨、好讀好懂的工作效率優先。
